# 主策略卖出验收与 prType=49 一手闭环设计

日期：2026-08-07
状态：待用户书面复核

## 1. 背景与目标

真实账户 `8890116049` 已完成收盘集合竞价一手买入验收：主策略在
2026-08-07 使用 `prType=11` 买入 `601326.SH` 和 `601375.SH` 各 100 股，
QMT 委托、成交回执、账户快照和本地账本一致。

下一阶段不开始正式建仓，只完成两组有边界的能力验证：

1. 主策略正常生成下一交易日计划，确认渐进建仓阶段没有 Drop；随后通过受审计的
   测试批次卖出一笔现有的一手持仓，验证主策略卖出链路。
2. 新建独立的 `prType=49` 探针策略，用真实账户完成“一手买入、下一交易日一手卖出”
   的完整盘后固定价格交易闭环。

两组测试完成后，主策略保持暂停，等待用户安排正式建仓。不得自动解除 100 股上限，
不得自动创建未来日期的执行授权。

## 2. 设计原则

- **账户账本统一**：两个策略操作同一个真实账户，因此共享账户级 SQLite 账本；批次、
  订单和监控按 `strategy_id` 隔离。
- **执行通道隔离**：主策略和 `prType=49` 探针使用不同 QMT 策略实例及不同桥接目录，
  不得争抢同一个 inbox、processing 或 active state。
- **不可直接修改已发布文件**：手工测试意图必须由工具生成新的不可变批次，自动重算
  checksum 并在暴露给 QMT 前登记账本。
- **失败关闭**：缺少账户匹配、当日授权、证券资格、官方价格、真实委托号或可信终态时，
  不得推断为成功，也不得扩大下单数量。
- **一次只启用一个执行策略**：主策略卖出测试与 `prType=49` 两日闭环顺序执行，
  不允许同一天同时授权两个真实执行通道。

## 3. 主策略卖出验收

### 3.1 正常计划预览

使用当前冻结的 CSI1000 B6-M + B2-S 配置和最新账户持仓，正常生成下一交易日计划。
计划保存在本地审计输出中，不写入 QMT inbox。验收要求：

- 信号日期和交易日期正确；
- 仍处于 Top30 渐进建仓阶段；
- 计划只包含最多两笔 BUY；
- 不包含 Drop 或 SELL；
- 已持仓证券会被跳过，候选向后顺延；
- 单槽目标金额仍为账户总值的 `0.93 / 30`。

### 3.2 受审计的卖出测试批次

新增操作员测试工具，从当前两笔可用持仓中显式选择一只，生成仅包含一笔 100 股 SELL
的测试批次。工具必须：

1. 要求显式指定交易日、证券代码和数量；
2. 验证证券确实存在于本地及最新券商持仓，且可用数量不少于 100 股；
3. 只接受 100 股整数倍，并在本阶段强制恰好 100 股；
4. 使用新的 batch ID、client order ID 和 `reason=operator_sell_probe`；
5. 使用主策略的 `CLOSE_AUCTION_LIMIT` 协议；
6. 原子登记不可变账本计划，再写 QMT 文件和 `.done`；
7. 不允许覆盖、原地修改或复用已经发布的批次。

QMT 继续在 14:57:05 使用 `prType=11` 和跌停价限价参加收盘集合竞价，
`MAX_ORDER_QUANTITY=100` 保持不变。

验收要求包括真实 QMT 委托号、100 股卖出终态、成交费用、本地持仓减少、券商账户快照
和现金/持仓二道对账一致。失败时不得开始 `prType=49` 测试。

### 3.3 主策略暂停

卖出验收通过后，主策略进入明确的 `PAUSED` 运维状态：

- 16:00 行情更新、股票名称、预测、日报和监控继续运行；
- 只生成不可执行的信号预览，不向 QMT inbox 发布 LIVE 批次；
- evening 监控将“经审计的暂停”识别为正常状态，而不是 `PUBLISH_MISSING`；
- 不自动创建未来日期 `LIVE_OK`；
- 只有新的用户指令才能退出暂停并开始正式建仓。

## 4. prType=49 独立策略

### 4.1 隔离边界

探针配置固定使用独立 strategy ID `csi1000_pr49_one_lot_probe`，桥接根目录为：

- Windows：`D:\qmt_bridge\pr49_probe`
- Mac：`/Volumes/qmt_bridge/pr49_probe`

该目录拥有自己的 `inbox/`、`processing/`、`outbound/`、`archive/`、`state/` 和
`logs/`。QMT 单独创建并编译一个探针策略实例，其 `BRIDGE_ROOT` 只指向该目录。

探针与主策略共用 `live_trading/data/csi1000_b6m_b2s_postclose_real.db`，保证同一真实账户
的持仓、现金、费用和收益只存在一套事实来源。账本查询和监控必须新增 strategy ID
过滤，避免某一策略把另一策略的批次误认为自己的发布或回执。

### 4.2 交易协议和门禁

- 执行会话：`AFTER_HOURS_FIXED_PRICE`；
- 信号价格类型：`AFTER_HOURS_CLOSE`；
- QMT 报价类型：`prType=49`；
- 数量：每单恰好 100 股；
- 证券：显式指定、当前未持有且经 QMT/交易所信息确认可参与盘后固定价格交易；
- 买入日：15:05 后提交，等待盘后固定价格成交及终态；
- 卖出日：下一交易日 15:05 后卖出同一只 100 股；
- 账户：必须精确匹配真实账户 `8890116049`；
- 授权：使用与主策略不同的 `PR49_LIVE_OK_YYYY-MM-DD`；
- 主策略在探针两日均保持暂停且不得存在主策略当日 `LIVE_OK`。

买入完成前不得生成卖出批次。卖出数量来自已导入的实际成交持仓，不根据原计划数量
推断。若第一天未成交，则第二天不得凭计划提交卖单。

## 5. prType=49 完整日志契约

此前 `prType=49` 曾出现“`passorder` 没有抛异常，但 QMT UI 中没有委托”的情况。
因此日志是本次测试的核心产物，不能只记录一行 `passorder called`。

探针每天同时写入：

- `logs/qmt_bridge_YYYY-MM-DD.log`：面向人工排查的文本时间线；
- `logs/qmt_events_YYYY-MM-DD.jsonl`：结构化、可机器验收的完整事件。

每笔订单至少记录以下阶段。

### 5.1 启动和环境

- 源码版本/文件 SHA、策略名称、QMT 可获得的客户端版本；
- 账户绑定结果、账户类型和脱敏账户 ID；
- `BRIDGE_ROOT`、execution session、`prType=49`、最大订单量和所有关键时间常量；
- timer 注册方式、注册结果和首次唤醒时间；
- 当日授权文件是否存在，授权决定在首次执行唤醒时冻结。

### 5.2 批次校验

- 文件认领、batch ID、strategy ID、trade date、mode、订单数量；
- checksum 计算值及匹配结果；
- 账户、环境、日期、证券代码、买卖方向和数量校验结果；
- 证券详情中与盘后固定价格资格有关的原始字段及解析结果；
- 失败时记录明确拒绝原因，不调用 `passorder`。

### 5.3 下单前快照

- client order ID、股票代码、方向、数量；
- `orderType`、`prType=49`、传入 price、quickTrade、strategy name、remark；
- 最新价、昨收、官方收盘价及其字段名、采集时间和有效性；
- 可用现金、可用股份、冻结数量以及本地费用预估；
- 完整参数的脱敏结构化副本。

### 5.4 API 调用与委托发现

- 调用前写 `PASSORDER_ATTEMPT` 并立即刷新文件；
- 记录 `passorder` 的返回值、返回类型、耗时；
- 异常记录类型、消息和截断后的 traceback；
- 无异常只能记录 `SUBMITTED_UNCONFIRMED`，不得写 `ACCEPTED`；
- 每轮 ORDER 查询记录查询时间、返回记录数、所有相关 remark、委托编号、状态码、
  状态文本、报单价格、报单数量、成交数量、撤单数量和错误字段；
- 查询不到 client order ID 时记录 `ORDER_NOT_OBSERVED`，并带累计等待时长和查询次数；
- 首次发现真实委托编号时才记录 `ORDER_OBSERVED` 和 `ACCEPTED`。

为控制日志量，无关订单只记录计数和脱敏摘要；与本探针 remark 匹配或疑似匹配的记录
保留完整业务字段。每轮查询都必须保留是否命中的证据。

### 5.5 回调、成交和终态

- `order_callback`、`deal_callback`、`orderError_callback` 的到达时间和关键字段；
- 成交编号、委托编号、成交数量、成交价、累计成交量；
- 委托状态的每次变化；
- 终结时汇总 API 是否返回、是否观察到委托、是否收到回调、是否成交及最终原因；
- `passorder` 返回但始终未观察到委托时，终态必须为 `ERROR`，消息固定包含
  `QMT order not observed after passorder`，不得写成普通 `EXPIRED` 或 `ACCEPTED`；
- 账户快照记录可用现金、冻结现金、总资产、全部持仓及探针证券可用数量；
- 日志文件写入失败回退到 FormulaOutput，但下一轮必须重试持久化并记录恢复事件。

结构化事件使用稳定事件名和字段，自动测试直接断言关键事件序列，不依赖文本模糊匹配。

## 6. 两日闭环状态机

### 第一天：一手买入

1. 用户确认显式证券代码和交易日；
2. 主策略保持 `PAUSED`，确认没有主策略当日授权；
3. 发布探针 BUY 批次；
4. 人工复核 Windows QMT 策略绑定、源码版本和日志启动事件；
5. 仅在上述检查通过后创建当日 `PR49_LIVE_OK`；
6. 15:05 后提交并导入 fills/account；
7. 验收真实委托号、`prType=49`、100 股数量、成交价和账户快照。

### 第二天：一手卖出

1. 只有账本和券商快照都显示探针证券实际持有且可用 100 股时才生成 SELL；
2. 重复账户、版本、日志和独立授权检查；
3. 15:05 后卖出同一只 100 股；
4. 导入回执和账户快照；
5. 验收探针仓位归零，现金、费用及盈亏与券商一致。

若任一天只观察到 API 调用而没有真实委托，测试失败并保持 100 股上限。若委托存在但
未成交，记录真实终态并由用户决定重试日期；不得自动扩大数量或换证券。

## 7. 监控与账本调整

- `batches`、发布完整性和回执完整性查询按 strategy ID 过滤；
- 账户快照和经济持仓仍按账户统一，不按策略拆分；
- 同一交易日如果意外出现两个策略的 LIVE 授权，监控产生 CRIT，两个通道均不得新增委托；
- 探针持仓存在期间，主策略预览可读取真实账户持仓，但不能发布执行批次；
- 探针闭环后的手续费和盈亏保留在主账户账本中，不做人工抹平或资本调整；
- Web 监控清楚标注主策略、探针策略、执行会话和当前 `PAUSED/ARMED/RUNNING/DONE` 状态。

## 8. 自动测试

至少覆盖：

1. 主策略预览确认渐进建仓阶段无 SELL，且预览不会写 QMT inbox；
2. 操作员卖出工具拒绝非持仓、不可用、非整手、超过 100 股和批次覆盖；
3. 手工卖出计划先入账本、后发布，checksum 和 client order ID 可复核；
4. 主策略 PAUSED 状态继续数据/预测/日报但禁止 LIVE 发布；
5. 两个桥接根目录互不消费文件，两个授权文件互不放行；
6. schema/config 同时支持 CLOSE_AUCTION/prType=11 和独立的
   AFTER_HOURS_FIXED_PRICE/prType=49，禁止交叉组合；
7. prType=49 在 15:05 前不下单，且每单最多 100 股；
8. `PASSORDER_ATTEMPT` 在 API 调用前持久化，返回后仅为
   `SUBMITTED_UNCONFIRMED`；
9. 委托查询逐轮记录，只有真实委托号才能产生 `ACCEPTED`；
10. API 返回但始终未发现委托时生成指定 ERROR 和完整诊断事件；
11. 回调、成交、重启恢复、账户快照和两日 BUY→SELL 状态转换；
12. 共享账户账本同时接收两个 strategy ID 的批次，但策略监控不会串批次；
13. live_trading 全量回归、parity gate、格式检查和 `git diff --check`。

## 9. 部署、授权与停止条件

实现完成并通过自动测试后，仍不得自动启用真实交易。Windows 需要复制并编译独立探针
策略，复核 `BRIDGE_ROOT`、真实账户绑定、100 股上限和启动日志。每个测试交易日均由用户
明确授权后才能创建对应的当日开关。

以下任一情况立即停止后续步骤：

- QMT UI 与结构化日志中的委托号或状态不一致；
- 没有观察到委托却出现 `ACCEPTED`；
- 实际数量超过 100 股；
- 两个策略同时获得 LIVE 授权；
- 回执缺失、账户快照缺失或现金/持仓漂移；
- 探针买入未形成实际可用持仓却生成卖出批次；
- 任何未解释的 QMT 重启、策略版本变化或日志中断。

主策略卖出和探针两日闭环均验收通过后，保持主策略 PAUSED，不继续正式建仓，等待用户
新的明确安排。
